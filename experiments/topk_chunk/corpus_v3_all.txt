检索增强生成（Retrieval-Augmented Generation，RAG）一词最早出现在 Patrick Lewis 等人于 2020 年发表的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》中，该工作发表于 NeurIPS 2020。论文的核心观察是：大型预训练语言模型虽然把大量事实知识存储在参数之中，但它们访问和精确操纵这些知识的能力依然有限，在知识密集型任务上往往落后于专门设计的任务架构。此外，纯参数化模型还存在两个长期悬而未决的问题：一是无法为输出提供可追溯的来源（provenance），二是无法随着世界的变化及时更新自己掌握的知识。

RAG 的思路是把两种记忆结合起来。参数化记忆（parametric memory）是预训练的序列到序列模型，负责语言生成；非参数化记忆（non-parametric memory）是维基百科的稠密向量索引，由预训练的神经检索器负责访问。两个组件被组合成一个概率模型并端到端联合训练：检索器采用稠密段落检索器 DPR（Dense Passage Retriever），根据输入查询返回最相关文档的概率分布；生成器采用 BART，在原始输入与检索到的文档共同条件下生成输出。检索到的文档被当作隐变量（latent variable）处理，训练时通过 top-K 近似对它们做边缘化，使检索器与生成器可以联合学习。

论文提出了两种不同的边缘化方式，对应两个 RAG 变体。RAG-Sequence 在生成整条输出序列时始终使用同一份检索到的文档，即先对 top-K 文档各自生成完整的序列概率，再按检索概率加权求和得到最终答案分布。RAG-Token 则允许每个输出 token 依据不同的文档来预测，生成器可以在多个来源之间切换取材，适合需要综合多份文档才能回答的问题。借助这种统一框架，RAG 可以像 T5 或 BART 一样微调到任何序列到序列任务上。

在知识源方面，所有实验统一使用 2018 年 12 月的维基百科转储（dump），并沿用前人做法把每篇文章切分成互不重叠的 100 词段落，最终得到约 2100 万份文档。每份文档用文档编码器计算向量表示，再用 FAISS 建立基于层次可导航小世界图（HNSW）近似的最大内积搜索（MIPS）索引，以实现快速检索。训练时每个查询检索 top-5 或 top-10 篇文档，测试时的 K 值依据验证集表现确定。这种切块、向量化再建索引的流程，也成为后来绝大多数 RAG 系统的标准做法。

实验覆盖了广泛的知识密集型任务。在开放域问答上，RAG 在 Natural Questions、WebQuestions 和 CuratedTrec 三个数据集上取得当时最先进的结果，并在 TriviaQA 上显著超过使用专门预训练目标的近期方法；值得注意的是，即便这些任务传统上由抽取式方法主导，不受约束的生成式 RAG 反而表现更好。在生成类任务（MS-MARCO、Jeopardy 问题生成）上，人类评估显示 RAG 的输出比纯 BART 基线更加事实、具体且多样；在 FEVER 事实核查任务上，RAG 与使用强检索监督的流水线方法差距不超过 4.3%。

RAG 的另一个关键优势在于知识可以更新。由于世界知识显式地存放在非参数化记忆（向量索引）中，只要替换或重建这个索引，模型掌握的知识就能随之更新，而不必重新训练参数。论文通过实验演示了这一点，指出这种可替换性为事实修正和知识维护提供了路径。这套代码后来开源在 HuggingFace Transformers 库中，RAG 也因此成为后续检索增强系统的奠基性方案。


嵌入（embedding）是把文本映射为浮点数向量的技术：一段文字经过嵌入模型编码后，会变成高维向量空间中的一个点。OpenAI 的 Embeddings 指南把嵌入定义为以浮点数列表表示的文本向量，其核心用途是度量文本之间的相关性——向量之间的距离被用来刻画语义关系，距离越近表示两段文本越相似，距离越远表示越不相关。这一"语义相近的文本拥有相近的向量"的假设，是相似度搜索、推荐、聚类、分类等一系列应用的基础。

衡量两个嵌入向量的距离有多种方式，指南推荐使用余弦相似度（cosine similarity）。它计算两个向量夹角的余弦值，取值范围从 -1 到 1，结果越接近 1 表示两段文本越相似，取值为 0 通常意味着不相关。由于余弦相似度只关注向量方向而不关注长度，它对文本长短的差异不敏感，因此成为文本检索中最常用的距离函数。在 RAG 系统里，用户查询会被编码成向量，再与知识库中所有文档向量逐一比较，返回最相近的若干段落作为上下文。

OpenAI 当前提供的第三代嵌入模型有两个。text-embedding-3-small 是性价比之选，输出维度为 1536，在 MTEB 基准上的得分为 62.3%，价格约为每百万输入 token 0.02 美元；与上一代 ada-002 相比，它性能更好而价格只有前者的五分之一左右。text-embedding-3-large 是能力上限之选，输出维度最高 3072，MTEB 得分约 64.6%，价格约为每百万 token 0.13 美元。两个模型的最大输入长度都是 8191 个 token，超长文本需要先切分再分别编码。

第三代嵌入模型采用 Matryoshka 表示学习技术训练，因此开发者可以通过 API 的 dimensions 参数主动缩短嵌入向量的长度，而基本不损失表征概念的能力。官方给出的对比是：把 text-embedding-3-large 截断到 256 维，其性能仍然超过未截断的 ada-002 的 1536 维向量。指南建议把维度调整放在检索管道的后续阶段进行，这样可以在存储成本与检索精度之间灵活权衡——先用完整维度建库，再按业务对延迟和成本的容忍度决定压缩比例。

指南列举了嵌入的典型应用场景：检索（按与查询的相关性对结果排序）、聚类（把语义相近的文本分组）、分类（按最相近的标签归类）、推荐（根据相关项目做推荐）、异常检测（识别与其他样本距离过远的离群点）以及多样性度量（分析文本相似度分布）。对于构建检索系统的开发者，指南展示了把嵌入向量存入向量数据库、再配合余弦相似度做语义搜索的完整流程，并提醒嵌入质量直接决定下游检索和生成效果的上限。

从工程角度看，使用嵌入的流程通常分两个阶段。索引阶段：调用 API 批量为文档生成向量，把向量与原文一起存入向量数据库或自建索引；查询阶段：把用户输入编码成同维度向量，通过最近邻搜索找出最相似的若干条记录。指南还提醒两点实践事项：单条文本超过 8191 token 时需要先切分再编码；查询与文档必须用同一个嵌入模型生成向量，不同模型甚至不同版本的向量空间互不兼容，混用会导致相似度失真。


Anthropic 在 2024 年 9 月发布的《Contextual Retrieval》文章中，先回顾了标准 RAG 的预处理流程：把知识库拆分成通常不超过几百 token 的小块（chunk），用嵌入模型把每块转换成捕捉语义的向量，存入支持语义相似度检索的向量数据库；查询到来时按语义相似度找出最相关的块，拼进提示词交给生成模型。文章同时指出，嵌入模型擅长捕捉语义关系，却容易漏掉精确匹配，因此建议配合 BM25 这类基于词法的排序函数。BM25 建立在 TF-IDF 概念之上，考虑文档长度并对词频做饱和处理，防止常见词淹没结果，特别适合检索包含唯一标识符或专业术语的查询，例如在技术支持库里搜"错误代码 TS-999"。

文章把传统 RAG 最大的缺陷称为"上下文难题"：文档被切成小块后，单块往往脱离了原语境，既难以被检索到，也难以被正确使用。文章举了一个 SEC 财报的例子——用户问"ACME 公司 2023 年第二季度营收增长了多少"，而某个相关块只写着"该公司营收环比增长 3%"，块内既没有公司名也没有时间范围，检索器很难把它与问题对上。文章还提到，以往用文档摘要、假设性文档嵌入、摘要索引等方法补充上下文的尝试，实测收益非常有限，这与本文方法有本质区别。

Contextual Retrieval 的做法是在嵌入和建立 BM25 索引之前，为每个块前置一段针对性的说明文字，形成"上下文化嵌入"（Contextual Embeddings）与"上下文化 BM25"（Contextual BM25）两种子技术。人工为百万级块写注释不现实，Anthropic 用 Claude 同时读取整篇文档与单个块，让模型生成 50 到 100 token 的简短上下文说明，并把这段说明拼在块的前面。借助提示词缓存（prompt caching），整篇文档只需载入缓存一次，即可为所有块复用，为每个块生成上下文的一次性成本约为每百万文档 token 1.02 美元。

评估指标采用 1 减去 recall@20，即相关块未能进入前 20 名检索结果的失败率。在代码库、小说、ArXiv 论文等多个知识域上的实验显示：仅用上下文化嵌入，就把 top-20 检索失败率降低了 35%（从 5.7% 降到 3.7%）；上下文化嵌入与上下文化 BM25 相结合，失败率降低 49%（从 5.7% 降到 2.9%）。在所有测试过的嵌入模型组合上，上下文化处理都带来了一致提升，其中 Voyage 与 Gemini 的嵌入模型表现最好。

在检索与生成之间加入重排序（reranking）还能进一步改善效果。初检通常先取较多候选块（文章用 top-150），重排序模型对每个候选按与查询的相关性打分，只保留前 K 个（文章用 top-20）交给生成模型，这样既能减少无关信息进入上下文，也能降低成本与延迟。实验显示，重排序与上下文化嵌入加 BM25 结合后，top-20 检索失败率共降低 67%（从 5.7% 降到 1.9%）。文章提醒，重排序会增加少量运行时延迟，需要在召回率与速度之间做权衡。

文章最后给出若干实施要点：切块的大小、边界与重叠设置都会影响检索质量，值得实验调优；为特定领域定制上下文生成的提示词（例如加入术语表）往往优于通用提示词；送入上下文的块数量并非越多越好，实测送入 20 个块优于 10 个和 5 个，但信息过多可能分散模型注意力；上线前务必持续做评估。各项收益可以叠加：上下文化嵌入加上下文化 BM25，再加上重排序，并送入 20 个块，是文中测试出的最佳组合。


Microsoft Learn 的《Retrieval-augmented generation (RAG) in Azure AI Search》页面把 RAG 定义为一种用自有内容为大型语言模型响应"接地"（grounding）的模式，用以扩展 LLM 的能力边界。与直接向模型提问相比，RAG 让答案建立在企业私有、可管理的内容之上，有助于缓解知识过时与模型编造答案的问题。页面同时强调，RAG 在概念上简单，工程落地却面临一系列现实挑战，需要认真设计检索与安全机制。

页面把 RAG 实现的主要挑战归纳为五类。一是查询理解：用户常提出复杂、口语化或含糊的问题，传统关键词检索在查询措辞与文档用语不一致时就会失效，例如用户问"远程办公政策"，文档里写的却是"telecommute"，检索系统必须理解意图而非只匹配字面。二是多源数据访问：企业内容散落在 SharePoint、数据库、Blob 存储等平台，需要在不打断正常数据运维的前提下统一检索面。三是 token 约束：LLM 输入长度有限，检索系统必须返回高度相关且精炼的结果，而不是整份文档倾倒。四是响应时间：用户期待秒级答案，检索必须兼顾彻底性与速度。五是安全与治理：向 LLM 开放私有内容要求细粒度访问控制，确保用户与智能体只能取回被授权的内容。

Azure AI Search 针对这些挑战提供两条路线。其一是"代理式检索"（agentic retrieval）：一个完整的 RAG 管线，由 LLM 负责查询规划，把复杂问题拆解成多个聚焦的子查询并行执行，结合对话历史理解上下文，最终返回为聊天补全优化的结构化响应，内置引用来源、查询活动日志与可选的答案合成。其二是"经典 RAG 模式"：应用发出单一查询，由混合搜索加语义排序完成检索，再交给应用侧编排的 LLM 作答，架构更简单、组件更少、延迟更低，适合需求简单或必须使用正式发布（GA）功能的场景。

在提升召回与相关性方面，页面给出的核心建议是混合检索（hybrid search）：同一个查询同时走关键词（非向量）与向量两条路径，把两条路径各自命中的最相关结果融合成统一结果集，召回优于任何单一方式。在此基础上，语义排序（semantic ranking）按含义而非字面重新打分排序；评分配置（scoring profiles）可以加权特定字段或条件；向量查询还支持权重与最低阈值等微调参数。针对术语不一致的问题，页面还提供同义词映射（synonym maps）机制作为补充。

检索质量很大程度上取决于内容准备。页面列出的支持能力包括：对大文档做自动切块（chunking），使各部分可以被独立匹配检索；通过向量化步骤生成用于向量查询的嵌入；支持 50 多种语言的文本分析器与多语言向量，应对多语言内容；对图片和 PDF 提供光学字符识别、图像分析与图像言语化等技能；用增量索引保持内容新鲜。页面强调，RAG 的效果取决于合适的内容、聪明的查询与能挑出最佳块的查询逻辑三者的组合。

在方案选型上，页面建议：构建新的 RAG 实现、面向智能体或聊天机器人、查询复杂或对话化、需要带引用的结构化响应时，优先选择代理式检索；只用 GA 功能、追求简单快速、已有编排代码要保留、或需要对查询管线做细粒度控制时，选择经典 RAG。页面还介绍了 Foundry IQ，它作为面向智能体的知识层单一端点，把企业内容转化为可复用、感知权限的知识库，底层即使用代理式检索。
