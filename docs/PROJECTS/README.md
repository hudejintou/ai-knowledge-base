P1：提高可信度（建议完成）

- [ ] 检索层指标：在评估中单独统计 recall@k（检索是否找到标准段落），与最终回答正确率分开记录，便于定位问题出在哪一层。也可用于切块前后召回对比（即候选值的方案 B）。
- [ ] 盲测题集：用新语料在不看结果的前提下设计题目，冻结后再跑对比。这是检验"工具版是否稳定更优"的唯一可信方式。
- [ ] 集成测试：增加一条不 mock 检索的端到端测试（用 fakeredis 和小型测试语料），覆盖入库、检索、问答全链路。
- [ ] 评估脚本收敛：eval_all、eval_holdout、topk_* 等脚本逻辑有重叠，统一到 eval_tools 或一个入口，减少结果不一致的风险。
- [ ] 入库接口加固：目前只把连接类错误降级为 503，`delay` 的其他异常（如依赖缺失导致的 ModuleNotFoundError）仍会变成 500。应对 `delay` 的所有异常统一降级并记录日志。
- [ ] 统一错误响应格式：DRF 对非法 JSON 返回的是 `{"detail": ...}`，业务错误返回的是 `{"error": ...}`，两者应统一。

P2：可选增强（视时间决定）

- [ ] 接口鉴权与限流：至少加一个 API Key 或 token 校验，防止接口被滥用消耗智谱额度。
- [ ] 流式输出（SSE）：让回答逐步返回，改善体验。
- [ ] PDF / Word 解析：支持文件上传，解析后走同一条切块入库流程。
- [ ] PostgreSQL 替换 SQLite：解决多进程并发写入问题，同时更贴近企业环境。
- [ ] 向量索引：当前是全表扫描计算余弦相似度，数据量增大后可考虑 pgvector 或 FAISS。

明确不做（写进已知限制）：多租户、细粒度权限、用户体系。这些超出当前主线，面试时如实说明即可。

- **已知限制**：
  - 工具模式每题多一次模型调用，耗时和成本高于基线。
  - 评估结果均为单次运行，题集由作者设计，HOLDOUT_SET 与 MULTI_SET 都不是盲测。
  - 文档只接受纯文本；无流式输出；SQLite 不适合并发写入；无鉴权。
  - 切块按字符硬切，不考虑句子边界；切块前后的检索效果尚未对比。
  - `sources` 返回整块正文，块较长时前端需自行截断。
  - 测试入库使用重复句，未覆盖真实长文档。
  - `pending` 状态无法区分"排队中"与"任务失败未补算"。
